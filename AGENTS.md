# Maintaining this repository

These instructions apply to authors of the Linux tool skills. Preserve unrelated assessment methodologies.

- Start with `GETTING_STARTED.md` for Linux setup and source ingestion. Use `authoring/schema.md` and `authoring/create-skill.prompt.md` when adding skills.
- Each tool is independently installable as `skills/<name>/SKILL.md`. Keep every required resource inside its folder; no umbrella or shared runtime dependency.
- Assume workers already use the CLI competently and can adapt/retry within a task graph. Help them choose an existing tool and load operational domain knowledge on demand. Keep entrypoints small but useful, with conditional task references for substantial depth; omit generic advice, repetition and rigid investigation rituals.
- During ingestion, bring each revisited existing skill into the current schema: reconcile the whole affected task, correct/merge weaker text and trim or move unrelated branches rather than only appending examples. An already conforming skill or a source with no useful delta needs no cosmetic change. Record schema version and actually reviewed skills in existing intake reports; identify unreviewed skills at batch completion.
- Put the activation contract near the top: read the entire SKILL.md before acting, identify required steps/resources for the selected task, and distinguish conditional references. Review the first 150 lines as a partial-read check, not a claimed harness limit. Use a small checklist or task map when it helps; keep short skills short. Follow authoring/schema.md for completion evidence and missing prerequisites.
- Account for actually used tools/tasks in the intake report. Similar coverage in another tool is not a reason to omit discovery; a useful verified narrow task is enough. Preserve operational procedures and domain reasoning in conditional references. Keep authoring execution restrictions separate from permitted documentation, and unavailable runtime checks separate from acceptance. Follow the schema coverage rules.
- Write for the supported task, with commands, meaningful results and the next decision connected. Add examples for distinct workflows or recovery decisions, not to meet a quota. Label invented sample output as illustrative.
- Supporting files are optional and serve substantial conditional working instructions or reusable execution. Keep review dates, source-document/page trails and test history in the existing intake reports and validation record under `docs/`, mapped to the affected skill. Preserve required attribution; retain primary-documentation links in the skill when they help execution or recovery.
- Verify command semantics and important interpretations. Report documentation review, actual execution and agent outcomes accurately; do not invent test results.
- Target the single Linux distribution/image the user controls. Current ingestion improves guidance; a later on-box pass discovers binaries and enriches existing references or references/environment.md with verified absolute invocations and relevant image/version/option facts. These shared image facts may be committed with the skill. Keep node-specific/private facts and raw input in ignored work/, and raw test artifacts in runs/. Do not fabricate paths now or add a per-host deployment-copy layer.
- Update the README catalogue for accepted skills. Run the repository checker and relevant tests after packaging changes; test changed command behaviour in an appropriate Linux fixture when available.
- Keep source intake and example commands within the user's authorisation. Skill installation does not install tools or apply the optional settings in `profile/`.
