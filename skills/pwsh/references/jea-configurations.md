# Interpret acquired JEA files and session evidence

Use acquired complete `.pssc` session configuration and referenced `.psrc` role capability/module files with their source/time identity. Run the entrypoint's parser on each selected file, then read the actual declarations and nested function bodies as text. Parsing is not registration or execution; a copy in a user's Documents directory does not establish which endpoint loaded it.

Connect the files to the registered endpoint name, role mapping and selected account. `ConfigurationName` names a registered endpoint, not necessarily the PSSC basename. A failed connection to a default endpoint does not establish a bad password or rejection by a different named endpoint. Record client transport, endpoint and error separately. The source filename alone cannot resolve that relationship.

For the selected configuration, inspect `SessionType`, `LanguageMode`, `RoleDefinitions`, `RunAsVirtualAccount` and any `RunAsVirtualAccountGroups`. A RestrictedRemoteServer normally uses NoLanguage with a small default command set. ConstrainedLanguage is a different mode; language constraints and command visibility are separate controls. A command-resolution error does not prove the executable is missing from the machine.

Virtual-account execution differs from the connecting account. Defaults depend on member-server versus domain-controller role; explicit virtual-account groups can replace administrator-group membership. The configuration flag alone is not an observed token or successful file operation. Preserve connecting identity, run-as context and the operation's actual result separately.

Follow the selected role capability names to their resolved files/modules. Duplicate capability names and module search order can leave the effective file uncertain. Multiple applicable roles can widen the combined command/parameter set. Inspect `VisibleCmdlets`, `VisibleFunctions`, external commands, providers, parameter constraints and `FunctionDefinitions`; a function body being defined does not alone prove it was made visible.

Custom function bodies can use capabilities beyond the caller's exposed command set, while constrained proxy commands still matter. Trace supplied parameters through validation to the actual operation. A textual prefix or wildcard check alone does not establish that the resolved filesystem object is inside the intended directory. Record the missing resolution/containment evidence and recommend reviewing the handler's validation and intended allowlist; do not invoke an acquired handler or change paths/links to reproduce an escape.

If a transcript is available, compare its selected endpoint/account, permitted-command list and relevant result with the acquired files. Keep truncated declarations, missing role files, registration changes and unobserved run-as identity as concrete gaps. Finish with supported configuration facts and the next evidence needed to establish effective policy; no successful bypass, privileged read or deployment change is implied by offline parsing.

Primary guidance: [session configuration and identities](https://learn.microsoft.com/en-us/powershell/scripting/security/remoting/jea/session-configurations), [role capabilities and custom functions](https://learn.microsoft.com/en-us/powershell/scripting/security/remoting/jea/role-capabilities), [language modes](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_language_modes), and [endpoint auditing](https://learn.microsoft.com/en-us/powershell/scripting/security/remoting/jea/audit-and-report).
