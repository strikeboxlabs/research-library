# Interpret an existing forwarding command

Review the acquired command, client location, SSH-server identity, effective options/configuration and selected application response. This task interprets existing evidence; it does not start a new tunnel or change listener/login policy.

For `-L bind:port:host:hostport`, the listening socket belongs to the SSH client and the destination connection is made from the SSH server. For `-R bind:port:host:hostport`, the listener belongs to the SSH server and the destination is reached from the SSH client. Local/remote describe roles in that SSH connection, not permanent labels for the operator's workstation and another machine. A command launched on a second host can reverse those everyday labels.

Interpret destination loopback on the side making that connection. Compare the exact destination port with independently observed application configuration/listener evidence; similar numbers are not interchangeable. A browser page shown later does not repair a mismatched recorded command. Missing bind address does not establish exposure on every interface: listener policy/defaults and effective configuration matter.

Separate authenticated SSH transport, requested forward/listener creation, actual destination connection and application response. `-N` requests no remote command; `-f` backgrounds the client after authentication, rather than executing the forwarding command on the server. `-p` selects the SSH transport port, not either forwarded application port. Starting the client without credentials for the destination application does not remove SSH-server authentication requirements. `ExitOnForwardFailure` handles forward setup failures, not all future connections to the destination. A retained shell login alone is not a working tunnel. Root login is not a generic forwarding prerequisite; the selected account's permission and listener-port privilege are the relevant questions. Do not enable root login or alter forwarding restrictions to reproduce a source's example.

Finish with the supported mapping, actual connection/application observations and unresolved port/policy/lifetime discrepancies. A stop message without inspecting the tracked connection/listener can leave cleanup uncertain. See [OpenSSH forwarding semantics](https://man.openbsd.org/ssh.1) and [server listener policy](https://man.openbsd.org/sshd_config.5).
