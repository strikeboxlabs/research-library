# Interpret a copy, archive and cleanup play

Use the acquired definition as text. Establish its deployed revision, inventory/host pattern, connection, execution identity, variables and resolved module versions before attributing filesystem behavior. A file owned by an account and periodic output timestamps are leads about execution, not the complete scheduler or task transcript.

Modern `ansible.posix.synchronize` and `community.general.archive` are collection modules; `ansible.builtin.file` is built in. Historical short names need the installed release/collection resolution rather than blind replacement. Missing collections or rsync are prerequisites to resolve separately, not evidence that a copied YAML definition ran.

For synchronize, map the controller/delegated origin and destination host, source trailing-slash layout and source/destination identities. Its `archive` option concerns rsync's copy attributes, not creation of a compressed backup. `copy_links: true` follows referents instead of retaining symbolic links. A writable source tree can change those referents or race copying, so a trusted root pathname alone does not establish contained input. Inspect policy and link treatment without substituting another account's private files. Default link preservation and an explicit dereference request are different backup contracts.

For archive, inspect the exact path set, exclusions, format and destination on the executing host. A directory tree with gzip compression normally becomes a tar archive; a single file can instead be only compressed unless `force_archive` selects an archive. The `.gz` suffix alone does not decide the layout. Preserve reported archived/missing inputs and incomplete state; archive size growth does not identify which member changed or establish a coherent application snapshot.

For a later `file: state=absent` task, the selected directory and descendants can be removed. Review the actual resolved staging path and task ordering/conditions; deletion is not proof the prior copy/archive was complete. Keep a failed or partial backup distinct from a successful cleanup. Completion requires the relevant task statuses/recap and an independently listed, verified archive with the intended members; retained owner labels or timestamps alone are insufficient. Do not execute an acquired backup or its cleanup merely to understand it.
