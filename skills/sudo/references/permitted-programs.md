# Follow the permitted program through its inputs and helpers

Use the exact effective sudo listing, installed executable and readable deployed source/configuration. A similarly named repository file or trace is a lead until matched to the permitted program. This is a review procedure; it does not require invoking an elevated workload.

A grant for an interpreter plus one exact script path does not grant arbitrary `python -c` execution, but the permitted script can still consume caller-controlled data through stdin, prompts, files or configuration. Follow that data into the script's actual operations. Root ownership of the script does not make its inputs trusted. An `eval` of file content happens before a later result check, so a final "invalid input" message does not establish that no earlier effect occurred. Preserve the exact policy, source locations and input path; separate that review from running the elevated script.

For a permitted downloader, trace the output destination as well as the URL and response bytes. GNU Wget's `-O` opens/truncates the selected output using its process authority; shell redirection outside sudo instead uses the invoking shell's authority. A download permission can therefore be a privileged file-write permission. Establish which arguments the grant permits, destination ownership/link resolution and any later program consuming that path, without overwriting a privileged file to demonstrate the finding. A successful HTTP transfer does not establish later execution. If another process reportedly restores the file, retain actual observations separately from an inferred schedule; two different contents alone do not prove a one-second timer. See [GNU Wget output-document semantics](https://www.gnu.org/software/wget/manual/wget.html#Download-Options).

For a wrapper that writes configuration and invokes another privileged consumer, review both grammars. A character allowlist is not proof that the resulting configuration is safe for its reader. Establish how prompts, read/echo behavior, whitespace, quoting and output truncation affect the stored bytes, then identify the installed consumer and any files it sources. Shell-sourced configuration is executed in that shell's context; a similarly named declarative parser can behave differently. A wrapper can overwrite configuration before a later validation or activation error. Preserve the exact deployed implementation and those effects without invoking network activation or supplying a privilege-escalation input just to prove the finding. See [Bash dot/source behavior](https://www.gnu.org/software/bash/manual/html_node/Bourne-Shell-Builtins.html).

For a helper path such as `./check.sh`, inspect the process working directory, not just PATH or the parent script's location. Sudo normally preserves the invoking directory, but `CWD`/`runcwd`, login mode, the wrapper's own directory changes or a subprocess `cwd` can alter it. A slash-containing relative path is not resolved through `secure_path`. Establish the helper's resolved location and who can modify it; a repository copy is a lead until matched to deployed code. An argument list with `shell=False` does not make a caller-controlled executable path trustworthy. See [Python subprocess path resolution](https://docs.python.org/3/library/subprocess.html#popen-constructor) for that distinction.

With an explicit interpreter invocation, the target identity must be able to read the script; the script's execute bit alone does not provide the unprivileged caller with readable Python source. Keep file-mode observations separate from the interpreter and RunAs policy.

For a wrapper constructing an argv list, follow the child parser as well as shell handling. Fixed initial options do not necessarily lock that choice when later caller input can still be parsed as options. A list passed without a shell avoids shell expansion, but does not remove option semantics. Inspect delimiters, selected executable and argument validation without supplying a privilege-changing input. A command split on literal spaces also does not implement shell quoting; captured stdout/stderr and a printed prompt are separate from the child's checked status and identity.

A permitted executable may launch helpers by name. A Forge trace showing a `git` command is a lead about helper invocation, not proof that a caller-controlled PATH survives sudo or that a replacement would run. Check `secure_path`, RunAs identity, environment permissions, helper search directories and the exact target version together. Application trace logging is not a complete syscall trace. Do not generalise a local build's behavior to an unreadable privileged binary or execute a modified helper to establish the policy finding.

`sudo -E` asks policy to preserve the **exported environment** and can be denied. A shell-only assignment such as `PYTHONPATH=/some/path` on its own need not be exported, so a following `sudo -E` failure does not prove that variable preservation is universally broken. Distinguish shell export state, sudo filtering and the target program's own startup rules. Preserve only the variable actually needed; inspect the permitted wrapper's imports, config and child commands before changing their environment.

For `SETENV` wrappers, inspect the environment consumed by every child as well as the wrapper itself. An absolute executable path fixes lookup but not its runtime configuration. Clearing `PERL5LIB`/`PERLLIB` alone does not address Perl startup options or debugger configuration; inspect `PERL5OPT`, `PERL5DB`, invocation and taint-mode conditions using [perlrun](https://perldoc.perl.org/perlrun). A curl child can similarly consume proxy settings. Record which settings survive and which operations occur before a later guard. A `NOSAVE` branch after network retrieval and XML parsing skips the later write, not those preceding operations. Review the code without invoking the elevated wrapper just to test that conclusion.

For a permitted `git pull`, include the working directory in the policy assessment. The chosen repository can supply local configuration and executable hooks, so an exact executable/subcommand restriction alone does not establish a passive update. A Linux `post-merge` hook may run after a successful merge-path update, including a fast-forward; an already-current checkout or conflicted merge is different. Inspect the selected repository, effective hook path, script and ownership checks before concluding that a listed grant permits execution of a particular hook. A GitLab webhook merely explains what launched the local command; it is not that local hook. Do not invoke the elevated pull just to discover its effects.

For a permitted SSH client, options and configuration can select **local** helpers. `LocalCommand` runs after a successful connection when `PermitLocalCommand` is enabled; the remote login name does not establish the local helper's identity. Inspect the RunAs user, argument pattern and local command features together. A path-only or broad-argument grant is not inherently limited to reaching a remote account. Record the capability without launching a privileged shell to prove it. See [OpenSSH client configuration](https://man.openbsd.org/ssh_config.5) and [Git hook events](https://git-scm.com/docs/githooks).


For a privileged diagnostic/profile collector, trace the actual input file selection and output/archive handling separately. A quoted destination variable prevents shell splitting but does not establish path containment. An existence/type check can follow a symlink and can race a later open; root ownership of the collector does not make a caller-writable input directory trustworthy. Inspect directory ownership/modes and the collector's treatment of links and concurrent replacement, without substituting sensitive files or invoking the privileged collector to demonstrate disclosure. A fixed-size tail captures only a suffix, not an arbitrary complete input; a generated archive may contain other sensitive diagnostics and needs its own access/retention review. Report the deployed code and observed metadata as a policy finding, keeping unverified file-content or runtime conclusions explicit.

## Presets and Python module directories

A permitted BBOT executable can load Python from `module_dirs` in a caller-selected preset when the argument grant permits it. The loaded code inherits the process identity. A fixed binary path, `env_reset` and `secure_path` do not constrain an explicitly selected module directory. Follow preset selection, readable/writable module paths and the installed loader's preloading/import/setup order; a directory-wide trust assumption can hide a different file from the reviewed one.

Metadata preloading and actual module import are different stages. Current BBOT skips files without expected class metadata during preloading, while actual loading executes the Python file before locating its class. `--dry-run` occurs after scan preparation, and `--force` continues through some setup/condition failures rather than granting authority. A malformed example or scan banner is not proof of module execution. When an authorized execution check is needed, invoke the exact permitted command with a reviewed module which logs its effective UID, and preserve that marker with the policy and inputs. Separate a marker observed during setup from proof that an event handler ran. An earlier observed effect can persist despite a later scan failure. See the [BBOT module API](https://www.blacklanternsecurity.com/bbot/Stable/dev/module_howto/) and deployed-version loader; no privileged scan is needed merely to read this policy.
