# Process a selected template resource

Read this entire SKILL.md before acting. Require the installed Remco version, trusted configuration/templates/backend data and approved destination and hook effects. Review the complete effective configuration before processing it. Finish with process status, the resulting file, validation/hook receipts and any requested application health; identify missing evidence explicitly.

Remco uses Pongo2 templates, not Go templates. Trace the selected backend endpoint/API, loaded key namespace, template source, destination and service action. A template can insert a backend string directly into another parser's configuration; successful rendering does not prove that the value is safe or syntactically valid for that parser. Review the selected template's validation and quoting rules.

For one controlled operation, use a dedicated configuration containing only the selected fixture resource. Inspect included resource directories, default backends, executable plugins/custom filters, template checks, resource/template reload commands, start commands and child-process configuration. Remove unintended effects from the fixture before execution. A configuration pathname alone does not limit processing to its first resource.

Set `config` to this reviewed fixture configuration:

~~~bash
remco -config "$config" -onetime
render_status=$?
~~~

`-onetime` selects one-time backend processing for every resource in that configuration. It is an actual rendering operation: destination files can change and configured commands can run. It is not a lint or dry-run flag.

A template `check_cmd` checks the staged render before destination replacement; a nonzero check leaves that destination unoverwritten. A template `reload_cmd` runs after its destination update. Inspect the command itself: a field named reload can invoke a service restart. Check the generated bytes and their intended destination, then the selected application's own validation and health evidence. A rendering error may coexist with other successfully processed resources; do not infer transaction-wide rollback.

Use [configuration options](https://github.com/HeavyHorst/remco/blob/master/docs/config/configuration-options.md), the [project overview](https://github.com/HeavyHorst/remco) and [CLI implementation](https://github.com/HeavyHorst/remco/blob/master/cmd/remco/main.go) when installed-version behavior differs. Binary location and backend availability must come from the controlled image.
