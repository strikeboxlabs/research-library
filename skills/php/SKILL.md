# PHP CLI reproduction context

Read this entire SKILL.md before acting. Establish the selected binary/SAPI, then choose configuration/source inspection, PHAR/upload review, PostgreSQL diagnosis or output encoding. When psql is unavailable and the task requires PostgreSQL diagnosis, read [the PHP connection procedure](references/postgresql-connection.md) fully before its commands; it requires an existing libpq service and a reviewed local snippet. For HTML encoding or dynamic SQL construction, read [output and SQL context](references/output-and-sql-context.md) fully before its checks. For offline Laravel CBC cookie/session analysis, read [cookie decryption](references/laravel-cookie.md) fully first; it requires the actual cipher and authorized key/envelope files. For an authorized Joomla template edit/process test, read [template process boundaries](references/joomla-template-processes.md) fully first; it requires actual edit authority, original bytes and a verified trigger. For an authorized Backdrop module/archive upload and direct PHP endpoint test, read [Backdrop module execution](references/backdrop-module.md) fully first; it requires actual installation authority, the selected format and tracked artifact/trigger. For validated/coerced inputs later used in a shell command, read [validation and argument boundaries](references/validation-and-arguments.md) fully first; it covers pure CLI reproduction and an authorized nc-backed form test. For serving a selected disposable web test, read [local web server](references/local-web-server.md) fully first. Finish with the observed configuration, served response, exact transformation, verified database identity or observed template process effect/restoration; lint or a CLI result alone cannot establish web-runtime behavior.

For existing Xdebug configuration or an IDE connection failure, read [debugger context](references/debugger-context.md) fully before diagnosis; match the PHP/Xdebug generation and CLI/web SAPI without triggering remote evaluation.

For FPM listener/worker attribution, read [pool and process context](references/fpm-pool-context.md) fully before interpreting the selected service configuration.

For a selected offline legacy checksum or deterministic upload-directory expression, read [exact checksum inputs](references/exact-checksums.md) fully before its diagnostic procedure. It requires known input representations and finishes with the observed digest and the transformation's limits.

Define `php_bin` as the intended executable, which may be a versioned binary rather than the default `php`:

~~~bash
"$php_bin" -v
"$php_bin" --ini
"$php_bin" -m
"$php_bin" -r 'echo PHP_VERSION, " ", PHP_SAPI, PHP_EOL;'
~~~

Record the binary, SAPI, loaded configuration and relevant extensions. CLI results do not establish the version/configuration used by Apache or FPM. An HTTP version header is a separate observation; testing local PHP 8.2 does not reproduce a service merely reporting 8.3.2. `-n` ignores ini files and may omit extensions, so use it only when that configuration difference is intentional.

For an open_basedir failure, match the effective web SAPI's directory-tree restriction, actual file resolution and process access. A permitted directory is not proof every file beneath it is readable, and a failed external-file read alone does not identify this setting as the cause. The directive is an additional PHP restriction rather than comprehensive process containment; it does not establish authorization for a file include or make log content inert. Inspect configuration and the original diagnostic instead of reproducing a private-file read. See [open_basedir behavior and limits](https://www.php.net/manual/en/ini.core.php#ini.open-basedir).

For a function supplied by a native extension, follow the selected startup options, actual ini/scan files and module identity. A keyword in an acquired php.ini describes disk configuration; a saved maps copy describes one past process, not the current listener. Correlate that capture's producer/time with the exact binary/SAPI and observed loaded module before asserting deployment. Merely loading an unreviewed extension, including during diagnostics, executes native startup code. Keep static acquired-file review separate from permitted runtime checks, and do not call an authentication function just to discover what library supplied it.

For an existing reviewed source file, define `script` and lint it before any intended execution:

~~~bash
"$php_bin" -l "$script"
~~~

Lint checks syntax, not application behavior, runtime dependencies, reachable classes or security. Normal PHP startup/configuration still matters. To execute a small reviewed snippet, `-r` accepts PHP code without `<?php` tags; keep shell quoting intact and pass variable input as arguments rather than interpolating it into PHP source. Running a supplied script or calling `unserialize` is code execution, not merely inspection of an artifact.

For a saved serialization handler, trace the acquired source without deserializing its input. Object restoration can invoke autoloading and `__unserialize`/`__wakeup`; when both methods exist, `__unserialize` takes precedence on supported versions. An `if (unserialize(...))` truthiness test happens after restoration; it is not validation before callbacks. False also represents a valid serialized false value, so retain diagnostics. A callback's file-write result is separate from object truthiness: inspect `file_put_contents` return handling and its overwrite/append choice. `__DIR__` means the defining file's directory, not the process working directory or a property string's apparent absolute directory; follow exact concatenation and filesystem resolution. Finish with the input-to-callback/dependency map and supported effects under the evidenced process identity, identifying missing code or diagnostics. See [restoration behavior](https://www.php.net/manual/en/function.unserialize.php), [magic-method precedence](https://www.php.net/manual/en/language.oop5.magic.php), [magic constants](https://www.php.net/manual/en/language.constants.magic.php) and [write results](https://www.php.net/manual/en/function.file-put-contents.php).

For a login/redirect source review, follow the unauthenticated branch through every later read/output operation. `header('Location: ...')` schedules a response header; it does not terminate PHP execution or establish authorization. Require the actual termination/return and surrounding control flow before treating a redirect as protection. A response can contain both a Location header and generated body. Keep web process identity separate from file owner and login name: a per-vhost account directive inside IfModule is configuration intent until the effective loaded module and observed runtime identity support it. Review these boundaries as data without retrieving private-key/credential contents to demonstrate a finding. See [header and termination behavior](https://www.php.net/manual/en/function.header.php).

For a request-method predicate, `!$method == 'POST'` groups as `(!$method) == 'POST'`, not as negation of the comparison. It combines Boolean negation with loose equality and does not express the intended method gate. Use a defined scalar method and strict `$method !== 'POST'` when that is the requirement, then inspect actual termination and the later input/sink. A correct method check does not supply authentication, authorization or safe process arguments. Keep this as source/control-flow review; lint cannot establish the predicate's intended behavior. See [PHP operator precedence](https://www.php.net/manual/en/language.operators.precedence.php).

For a login/session source review, track the exact input used for authentication and the identity stored afterward. `$_REQUEST` composition and collision order depend on `request_order`/`variables_order`; cookies do not invariably participate or override POST fields. A form's `method=POST` does not prove that its handler uses `$_POST`. Require the complete handler and deployed web-SAPI configuration before asserting the precedence. Bind the session identity to the account actually authenticated, rather than another client-controlled source. Stored remote-address/user-agent fields are not enforcement unless later code checks them. Read [PHP request variables](https://www.php.net/manual/en/reserved.variables.request.php) for configuration differences.

When interpreting source, backticks invoke `shell_exec`, not `exec`; disabling `shell_exec` also disables the backtick operator. A blocked function explains that mechanism only, not whether the whole application is safe. `<?=` is the short echo form and is independent of `short_open_tag`; the shorter opening `<?` is configuration-dependent. Check the actual web SAPI's settings before attributing a failed reproduction to CLI settings. See [execution operators](https://www.php.net/manual/en/language.operators.execution.php) and [PHP tags](https://www.php.net/manual/en/language.basic-syntax.phptags.php).

A scheduled CLI launcher may include additional PHP files. Checking or hashing only the launcher does not establish the integrity of those dependencies. Trace `include`/`require`, configuration-driven prepend/append files, the working directory and effective include_path without executing the application. A bare `index.php` is resolved using PHP's include rules; it need not refer to the file a browser URL suggests. Check the resolved file and containing-directory permissions under the actual execution identity. `file_exists` only checks existence, and linting the launcher does not recursively validate the included code. See [PHP include semantics](https://www.php.net/manual/en/function.include.php).

For a handler that reads contents to validate them and later includes the same pathname, identify the two operations separately. `file_get_contents` returns data or false on failure; check `=== false` before interpreting content. A later include resolves and evaluates the file again, so an earlier content check does not bind the bytes used afterward. A rejected tag substring does not establish a trusted template. Prefer an allowlisted template identity backed by files/directories the caller cannot change, and review actual permissions and error handling. Keep this as static boundary review; a watcher or fixed delay cannot supply atomicity. See [file-read results](https://www.php.net/manual/en/function.file-get-contents.php).

`-d name=value` changes configuration for that invocation, subject to the directive's rules. For PHAR creation, `phar.readonly` controls whether PHP archives can be written; some changes are constrained by the startup ini. Reading an archive does not require a blanket machine-wide setting change. Keep any creation-specific override on the controlled CLI invocation and use a fresh output path.

For PHAR behavior, match the version and API actually called. PHP 8.0 stopped automatically unserializing PHAR metadata on ordinary archive loading; explicit metadata access is a different operation. A failed older demonstration therefore does not alone establish a patched application, harmless metadata or a missing gadget.

`getimagesize` can accept a non-image and return nonsensical dimensions. A `GIF89a` prefix plus reported dimensions is not proof of a valid decodable image or a pure image file. Likewise, `mime_content_type` classifies using magic-file information and returns false on failure; an `image/` result is classification, not complete image decoding or proof that no other content exists. Trace suppressed warnings and fallback branches rather than substituting the client MIME field for a failed detector. Use the intended image decoder and retain the original bytes. When wrappers or application transformations change a response, verify exact lengths and contents; do not invent missing bytes to make a parser accept it. See [MIME detection](https://www.php.net/manual/en/function.mime-content-type.php).


For upload-handler review, trace the original filename, client-supplied `$_FILES['file']['type']`, error status, content check and final destination as separate values. The MIME field is not PHP verification of the bytes. `move_uploaded_file` checks that its source came through PHP's HTTP POST upload mechanism; success does not establish a valid image. Ordinary CLI files do not become HTTP uploads merely by assigning `$_FILES`, so a failed CLI move is not a reproduction of the web handler.

Follow the exact variables used to build the stored name: `$extension` and `$ext` are different variables, and an omitted assignment leaves that step unresolved. A double extension alone does not explain the final filename or server execution. Check the complete handler and effective web-server mapping. An unconditional client message such as `Uploaded!` proves neither a successful move nor that a later URL addresses the uploaded file. See PHP's [upload fields](https://www.php.net/manual/en/features.file-upload.post-method.php) and [move semantics](https://www.php.net/manual/en/function.move-uploaded-file.php).
